# Railhead: developer notes

Read this first every session, together with `design-doc.md` (the design) and `CLAUDE.md` (how we work).
A fresh session should also read `plans/handover.md` if it exists.

## What the project is

Railhead (working title) is an isometric, low-poly railroad game set in 1866, built for phones first.
The whole game is one file, `index.html`, using three.js r128 loaded from cdnjs.
The full design is in `design-doc.md`. The original PDF it was converted from is kept in `docs/`.

## Platform decisions (2026-11-01)

These override the original design document wherever they disagree. Details are in `design-doc.md`, section 0 (decisions D1 to D11).

- Phones first, touch first, portrait and landscape. A computer with mouse and keyboard comes second.
- One HTML file, three.js r128 from cdnjs. There is no build step, no TypeScript and no Preact.
- The camera turns in 90-degree steps. The elevation is fixed at the true isometric angle.
- Avatar game: tap to walk there; press and hold walks towards the finger (D6, D7). Walking is part of M0 piece 1.
- Piece 1 uses the final low-poly models for the character, train, track and switch stands (D8).
- Size and speed targets are scaled down for phones (see design-doc section 0).

## How to test

1. Install the test tools once: `npm install`. This only fetches a copy of three.js r128 used by the tests.
2. Run every check: `npm test`. It must pass before every push.
3. Screenshots land in `test-output/`. That folder is not saved to git.

The checks serve the project on a local web address (saving in the browser needs one) and open `index.html` in Chromium through Playwright.
They use phone size (390 x 844 portrait, 844 x 390 landscape, with touch on) and fail on any console error.
Most checks open the page with `?paused`, so the game only advances when the check steps it.

Network note: the cloud test machine cannot reach cdnjs, because its network policy blocks it.
When that happens, the test script serves the identical three.js r128 file from `node_modules/three` instead.
The page itself still points at cdnjs.

A new game starts in the real world (the hub and Willow Ford, see "The real start"). Checks written for the M0 test yard's layout open the page with `&world=yard` (a new game, and `__railhead.newState`, then use the test yard); `check-boot.js`, `check-determinism.js`, `check-save.js` and `check-world-start.js` use the real start.

## Cargo (M1 package 2)

- **Items** (section "cargo (items and waybills)", after "trains"): `S.items` holds every freight item as columns indexed by item id (`waybill`, `where`, `alive`), plus `next` and the consumption log `used`. Ids are never reused. The API comment block at the top of the section lists the functions: `itemCreate`, `itemMove`, `itemCanMove`, `itemsAt`, `itemConsume`, `itemCheckConservation`. Other code must change items only through them. Each returns `{ ok, why }` and adds an event (`itemCreated`, `itemMoved`, `itemConsumed`, or `itemRefused` with the reason).
- **Places** (`where`): `CAR {stockId}`, `BAY {buildingId, bay}`, `CARRIED {actorId, carrier: HAND | HANDTRUCK | HANDCART, slot}`, `GROUND {x, z}` in hundredths, `STOCKPILE {jobId}`, `BUSINESS {businessId}`. The player's actor id is `'player'`. Cars now have stock ids (`consist[i].id`).
- **Limits**: a bay holds 8; by hand 1, hand truck 3, handcart 6; one way of carrying per actor at a time. A boxcar has 16 slots and a combine 8 (no long bundles). A flatcar takes long bundles, crates, pallets and machinery only (12 long or 8 crates: units of 2 and 3 out of 24). Bulk goods (logs, coal, ore) are not items.
- **Conservation**: `itemCheckConservation(S)` lists problems. Every item ever created is either alive in exactly one real place or logged once as consumed. Every place is within its limits.
- **Commodities**: `COMMODITIES` is the section 21 table (37 rows, prices in whole cents, null where it is not traded).
- **Destination tags**: `CARGO_TAGS` are WILLOW (W), HUB (T), HUBWH (H), RAILHEAD (R), OUTSIDE (O) and ANY (bays only). Each has a colour (colourblind-safe Okabe-Ito colours), a letter and a shape. `itemTag(waybill)` gives an item's tag.
- **Bays**: `BLD_BAYS` in "buildings" holds the bay positions as plain numbers, one bay in front of each of the freight shed's 4 doors. `S.bayTags.freightshed` holds the tags (default Willow Ford, Hub warehouse, Outside, Any). Change a tag with the command `{ t: 'setBayTag', b: 'freightshed', bay, tag }`. A non-matching bay is allowed and the move event says `mismatch: true`.
- **Drawing**: `itemPropShapes()` in "models" makes one low-poly shape per item type. "World rendering" draws them with one InstancedMesh per shape and one more for all the tag cards. `cargoDraw` in "drawing each frame" rebuilds the bays and the ground only when an item event happens (`cargoView.dirty`), when there is a new state, or when the camera turns. Carried items follow their actor every frame, through `cargoCarriedPose`, which builder W3 may replace. Items in a car, a stockpile or a business are not drawn. Code that changes items outside a tick calls `__railhead.cargo.redraw()`.
- **Testing**: `?debug=1`, then `rh.scenario('cargo')` or `?scenario=cargo`, gives 37 items (19 in bays, 15 on the ground, 2 in the boxcar, 1 in hand). A normal game starts with none; the Overland brings the first at 06:00 (see "Interchange and the Overland"). Test hooks are in `__railhead.cargo`.

### Provisional choices for the lead (not in the design doc)
- The tag letters and shapes are W Willow Ford (circle), T Hub town (square), H Hub warehouse (hexagon), R Railhead (triangle), O Outside (diamond) and A Any (ring). The colours are Okabe-Ito colours.
- A long bundle is refused on a handcart as well as on a hand truck. Section 9 says it goes "by hand" only.
- Flatcar mixing uses units: a long bundle is 2 and a crate or pallet is 3, out of 24. Machinery is 9 units and is refused in bays and for carrying.
- The placeholder towns are id 0 Hub and id 1 Willow Ford (`CARGO_TOWNS`), until real towns exist.
- An item's tag comes from its waybill. Outside goes to OUTSIDE. Construction or a camp goes to RAILHEAD. A warehouse goes to HUBWH. Town 1 goes to WILLOW, and anything else to HUB.
- The three loose crates and the barrel that stood on the freight dock in M0 are removed, because real items now stand in those bays.
- The per-item event history (`history` in section 20) is not kept, to keep saves small. The move events and the consumption log are the record. There are no free lists, because ids are never reused (that keeps the conservation check simple).
- Not built yet: the warning icon for an item in a non-matching bay. It is only flagged in the move event.

## Economy (M1 round C, builder C1)

- **Where the code is:** section "economy" (after "construction jobs"; pure sim). The comment block at its top lists `S.econ`, the API and the commands. Commands `useTelegraph`, `econOrder`, `contractAccept`, `contractDecline`, `creditDraw`, `creditRepay` in "commands"; `econTick` is step 8 of `simTick` (after the actors; `econTelBefore` notes a walk to the key before them). Page side: the telegraph panel (`telUi`, `telPanelUpdate`, `econOnEvent`) and the cash readout (`cashHud`) in "HUD and panels"; `econTelTap` in "input".
- **Money:** whole cents. `econPost` is the only thing that changes `S.econ.cash`; every change is a ledger entry `{ t, amount, category, counterparty, ref }` (categories in `ECON_CATEGORIES`). `econCheckMoney(S)` is the money rule (cash = starting cash + the ledger; credit owed = the credit entries; whole cents; known categories; time order), like `itemCheckConservation`.
- **Market:** `S.econ.market` buy and sell per commodity (section 21), with a per-commodity random walk (permille) moved every Monday 00:00 by up to 5% of base from the game's seeded numbers (`S.rng`, in commodity order), times the season factor, kept within 70% to 140% of base; 8 weeks of buy prices in `history`.
- **Telegraph key:** `econTelegraphKey()` is the hub depot's 'telegraph' use spot from `buildingSpots()` when the buildings section has it (C2), else worked out from the depot's layout entry (in front of the office bay window). Tap the bay window: `useTelegraph` walks there; on arrival `reachedTelegraph` opens the panel. Every economy command is refused (`econRefused`) unless the player stands within 3u of the key. ## How the game works (piece 1)

- **Simulation and drawing are kept apart.** The simulation advances in ticks of 8 game seconds, 10 ticks per real second at 1x. Drawing reads the state and blends between the last two ticks.
- **Commands.** Every action is a command (`walkTo`, `walkDir`, `useSwitch`, `useTrain`, `throwSwitch`, `trainRun`, `trainStop`, `trainSendTo`), applied at the start of the next tick. Commands carry whole numbers only (positions in hundredths), so replays match exactly.
- **Track.** The track is a graph of nodes and edges. A position is `{e, s, d}`: edge, distance from node A, and facing (+1 towards B, -1 towards A). `trackWalk` follows the switches as set. `trackScan` looks ahead for the stopping point and speed limits. A train facing a switch set against it stops 0.5u before the switch's block, not at the switch point.
- **Trains.** A train stores only its front position. Each car's position is found by walking back along the track. This is exact because switches under a train are locked.
- **Routes.** A* over directed edges (length plus 20u per diverging switch), trying both directions of travel. The switches are set instantly, as M0 allows, and locked. Each lock is released once the whole train has passed.
- **Player.** Tap to walk (`walkTo`, `useSwitch`, `useTrain`) follows a path from the walk grid (section "walk grid and path-finding", design-doc 11): one 0.5u grid over the whole map (the test yard 240 x 240 cells; the real start 672 x 256, see "The real start"). Blocked cells: building footprints grown by the player's radius (0.25u), any cell not flat at its corners, edge midpoints and centre (hills), and the cells under trains, which are stamped in at each query so the grid itself stays static. Costs: grass 1.4, platform and freight dock 1.0. While the player pushes the handcart, a second cached grid (made from the first on first use) also blocks the platform and the freight shed with its dock (`carryNoCartRects`, they have steps), so the path goes round them. The grid is cached per track and rebuilt only when the track changes (`walkGridSig`, and `buildTrack` clears it). A* is deterministic (whole-number costs, fixed neighbour order, ties by cell index), then the path is string-pulled (smoothed along clear straight lines). The path is never saved: it is worked out again every tick from the saved state (a memo keyed by start cell, target cell and train cells skips repeat work), so a moving train simply gives a new path round it, and a save loads to exactly the same walk with no new saved fields. A target inside a building, on a hill or in an area that cannot be reached is moved to the nearest cell that can be; the walk then ends there with the "Something is in the way" message (a train that stays in the way leaves the player standing beside it). A player inside a blocked cell (old save, teleport) first steps out to the nearest open cell. Press and hold (`walkDir`) is direct steering: a move into a train, hill or building tries its x-only and then z-only part, so the player slides along walls. A switch throw takes 0.5 game minutes at the stand, and only starts within 1.5u of it when the walk ended short. A tap on the train walks to within 1.5u of it (camera side preferred when both sides can be walked to straight; a side inside a building or on a hill gives way to the other side, reached round the train's end), then opens its panel.
- **Track and walking (provisional, for the lead):** design-doc 11 says track is impassable except at grade crossings and platform-end crossings. The M0 game lets the player cross track anywhere and throw switches from beside it, so for now track cells are walkable at the grass cost. Making track impassable needs crossings to exist first.
- **Path speed (test machine, software drawing, desktop CPU):** grid build about 3 ms; a typical path search (round the depot) about 0.01 ms; a long one across the yard about 2 ms (6,600 cells); the worst case (a goal that cannot be reached, so the whole connected area of 21,600 cells is searched, as when a train cuts it off) about 5 ms. A sim tick while walking about 0.2 ms. The worst case can repeat every tick only while a train keeps a target cut off.
- **Models.** Built in code from the style test page shapes. Each vehicle or body part is merged into one mesh with vertex colours and one shared material.
- **Build tool (piece 2, M0 instant build).** The Build button (top right, or the B key) turns on build mode: one finger draws track instead of walking; pinch and two-finger pan still work. A drag that starts on a track end (brass ring) continues it; one that starts on a straight places a switch there (5u through leg, radius 10u 30-degree diverging leg, on the side the finger moves to) and carries on from the diverging leg; one that starts on open ground starts a free piece heading the first drag direction (snapped to 15 degrees). The plan follows section 6: straight within 1 degree, else arc then straight (largest radius, 15-degree straights, nearby straight track's heading first, ends snapped to 1.6u parallel offsets); an end within 0.5u of a track end joins it with a straight, arc, arc + straight, straight + arc or S-curve. The ghost is green (valid), amber (ground more than 0.3u off the bed: needs earthwork) or red with the reason in the label. Red covers: radius by class, reverse curves without the straight, closer than 1.6u to other track or crossing it, building clearance (if `buildingFootprints()` exists), off the map, a train on the track, too little straight for a switch, and anything `trackValidate` finds. On release, Lay track / Cancel appear; Lay track sends `{t:'buildTrack', ...}` (whole numbers only), which re-checks and applies or refuses with an event. If the game is paused, Lay track runs one tick so the track appears at once. Splitting an edge keeps its id (it is shortened) and appends the rest.
- **Instant build parked behind `?debug=1` (D10).** The designer cut the M0 instant build; its code stays but only works with `?debug=1`. Without it the Build button and planning (ghost, green/amber/red, label) still work, but after release the button beside Cancel is Stake it (a construction job, see "Construction jobs" below) instead of Lay track. `send()` (the page's command intake, so also `__railhead.send` and `rh.send`) asks `buildIntakeRefusal()` in the build tool section first: without `?debug=1` a `buildTrack` command never reaches the queue and a `buildRefused` event (with `debugOnly: true`, recorded in `buildTool.refused`) shows "Cannot lay that track: instant track laying is switched off ...". Why there: the sim tick must never read page flags, or the same commands could give different results depending on the address; gating at the door where the page hands commands to the sim keeps `simTick`/`simRun` identical with debug on or off (the sim-only checks still build track through `simTick` directly). `buildTool.instant` says which mode the page is in.
- **Test hooks.** `window.__railhead` gives access to the state, `step(n)`, `send(cmd)`, `newState`, `simRun`, `stateHash`, `exportSave`/`importSave` and `toScreen`.

## Carrying (M1 package 1)

- **Where the code is:** the end of the "player" section (`carryActorTick` and the `carry*` functions, after `playerTick`), the commands `carryPick`, `carryPut` and `carryTool` in "commands", `modelHandTruck`, `modelHandcart` and `TOOL_STACK` in "models", `carryDraw` and `carryItemPose` at the end of "world rendering", the readout (`carryHud`) in "HUD and panels", and `carryTap` in "input". The item store itself is the cargo section's (builder W2).
- **How it runs:** `carryActorTick` replaces the direct `playerTick` call in `simTick`. A pick-up or put-down in progress (`P.act.k` is `pick` or `put`) is counted down there; otherwise `playerTick` walks as before, and afterwards the carry code notices arriving at an item, bay or tool spot (`P.use.k` is `pick`, `put` or `tool`) and starts the 0.2-minute action if within 1.5u. The walking code is untouched, so path-finding can change underneath it.
- **Carried items** are at `{ kind: 'CARRIED', actorId: 'player', carrier, slot }`. `carrier` is `HAND`, `HANDTRUCK` or `HANDCART`, from the tool pushed (`S.player.tool`, null or an index into `S.tools`). Slot 0 fills first; Put down takes the top slot. Taking a tool moves a hand-held item onto it (refused for a long bundle). A loaded tool cannot be left. Tools are taken and left only at their parking spots (`TOOL_PARK`, east of the freight shed, on the side away from the track), saved in `S.tools`.
- **Handcart:** may not go on the platform or the freight shed and its dock (`carryNoCartRects`, from the building layout plus 0.2u); a step that would enter is undone and the walk stops with a message. It can still put items into the bays from the track side of the dock (within reach). Known gap: the walk grid does not know about the handcart, and the platform and dock are its cheapest cells, so a path may lead onto them and the handcart stops at the edge; the walk grid should block those cells while a handcart is pushed (a follow-up for the path-finding owner).
- **Taps:** a tool spot takes or leaves that tool; an item picks it up if there is room; while carrying, a bay or the dock puts the top item in that bay (dock taps go to the nearest bay, as the cargo section draws ground items at ground height); by hand, the ground puts the item there. With a tool, a ground tap just walks; the readout's Put down button (or F) puts an item down beside the player.
- **Drawing:** the pushed tool stands ahead of the player (`CARRY_PUSH`); the hand truck leans back round its axle. Arms are forward 70 degrees carrying by hand, 45 degrees pushing, and dip during an action. A brass progress ring above the head shows any timed action, switch throws included.

## Passengers (M1 package 5, builder C4)

- **Where the code is:** section "passengers" (after "player", before "sim tick"; pure sim): `PAX` (all the numbers), the store `S.pax` (its comment block lists every field), stations (`paxStations`), the queue, ticket sales, boarding, the commands' code and `paxDebugScenario`. `paxTick` is step 8 of `simTick`. Commands `staffWindow { st }` and `leaveWindow` in "commands". Drawing: the end of "people (crowd)" (`paxView`, `paxLook`, `paxDraw`, called from `render()` after `updateCrowd`). Page side: `paxTap` in "input" (a tap within 34 px of a ticket window), and in "HUD and panels" the staffing readout (`#paxDesk`, with Leave) and the window's "Tickets (n)" button (`.paxWin`), in `paxHud`.
- **Stations:** read from data, never hard-coded. With C2's station table (`stationsOf(T)`) each station names its platform and depot, and the depot's `ticket` use spot (`buildingSpots()`) is where the player stands to sell; the window is 0.67u behind it. Without it (the M0 test yard, which has no table) each platform footprint is a station (the first is the hub) with its nearest depot, and the window is on the depot's track-side wall 0.35 of its width from its middle (where the recipe draws it). Cached per world. A station's edges are 0.8u past its platform's ends.
- **Travellers:** whole-number positions (hundredths), saved with their path (the way worked out on the walk grid, round buildings, hills and standing trains, when they set off somewhere). They walk 27 hundredths a tick (2.0 u per game minute). A step into a train waits; after 4 ticks the way is worked out again. States: `queue` (in line), `wait` (ticketed, on the platform), `board` (to a door), `aboard` (in a car, not drawn), `off` and `leave` (walking to the station's edge, then gone). Their own random numbers (`S.pax.rng`), so other systems are untouched.
- **Rates:** hub one traveller every 20 game minutes on average, Willow Ford every 45 (each gap 0.5 to 1.5 times that, in whole ticks), only 06:00 to 21:00, appearing at a random edge of their station and wanting the other station. At most 24 waiting per station (queue, platform and walking to a door); while that many wait, no more come. Plus 1 to 3 off each Overland visit (when it sets out its cars), appearing beside its engine and walking to the hub's queue, for Willow Ford.
- **Ticket window:** tap the window (or its "Tickets (n)" button, shown while people queue): the player walks to the staff spot; arriving there staffs it (`deskStaffed`), facing the queue. While staffed and the first in line is within 1.5u, a ticket takes 30 game seconds (counted in 8-second ticks with the remainder kept, so the average is exact). Any walk or action, or Leave, stops it. Fare: 4 cents a mile, at least 10 cents; the hub to Willow Ford is 10 miles (160u, section 15) so 40 cents. Each fare is posted with C1's `econPost(S, cents, 'fares', 'Ticket, Hub to Willow Ford', { kind: 'TICKET', id }, ev)`: one ledger entry per ticket, and the cash goes up. Counts per station in `S.pax.sold` and `S.pax.cents`.
- **The queue:** places 0.6u apart along the platform from beside the staff spot, then back in a second row, on open walk-grid cells inside the platform (24 places).
- **Giving up:** a traveller still in line 60 game minutes after arriving goes home (no conductors in M1), and the station's count `S.pax.rep[station]` goes up (the simple reputation counter, for M2).
- **Boarding:** a passenger car (`PAX.SEATS`: combine 12, coach 30) of a train of ours standing still (not running, routed or turning) with its centre beside the platform's track edge. Its doors (`PAX.DOORS`: the combine's one passenger door at its passenger end, 1.25u from its centre; a coach two) have boarding spots 1.3u out on the platform; a door up to 0.5u past the platform's end still serves it, its spot pulled 0.3u inside the end (No. 1 stopped mid-span at Willow Ford leaves the combine's door just past the 16u platform). At each door, one traveller every 6 game seconds (0.1 minutes): those for this station step off first, then ticketed travellers board in id order, never past the seats. A train that moves off sends the walkers back to waiting. Which trains take travellers (`paxTrainServes`): a train on the timetable (C3's `S.tt` services) only while its run is at this station and calls at the traveller's station later on; a train off the timetable (driven by the player) always.
- **Departure board:** one board per station, C3's station card (`ttCardHud`, shown while the player is within 12u of the station's order board), now listing the next 4 departures (`ttBoard` showed 3; changed by C4). For other code, `stationDepartures(S, stationId)` gives the next 4 departures as data `[{ time, train, to, platform, state }]` from C3's services (`S.tt.services`, days and stop times), soonest first within the next 24 game hours; a service that already left today gives tomorrow's run; state is On time, Late or No engine. Platform is always 1.
- **Drawing:** travellers use the crowd's 15 instanced meshes (room for 96 per kit after the walkers), so they add no draw calls when a crowd is shown, and at most the crowd's 30 (with shadows) when it is not. Looks from their id (`crowdDescribe`, never railroad staff or a conductor). On a platform or the dock they stand on its top. In line they face the window; waiting, the track.
- **Saving:** schema 9 (C1 took 6, C2 7, C3 8): the 8 -> 9 step adds an empty `S.pax` (`paxNewStore`); `paxCheckSaveShape` checks it on load. The sample `save-v9.json` holds a traveller in line and one with a ticket.
- **Testing:** `?debug=1&scenario=passengers` or `rh.scenario('passengers')` (the real start): 08:00, 20 in line at the hub's window and 20 ticketed on the platform, the player near the window. Hooks in `__railhead.pax`.

### Provisional choices (passengers, for the lead)
- Rates: hub every 20 game minutes, Willow Ford every 45, from 06:00 to 21:00; 1 to 3 off each Overland visit; at most 24 waiting per station.
- The ticket window is staffed from outside, standing at it on the platform (the depot's inside is not walkable); the queue runs along the platform from there.
- One passenger door on the combine, at its passenger (windowed) end; travellers step off before others board.
- A train off the timetable takes travellers at any platform, and they stay aboard until it stands at their destination's platform; a timetabled train only for its later stops.
- Alighting takes the same 0.1 game minutes per door as boarding.
- Travellers who stepped off walk to the nearer platform end and vanish there (no town yet).
- The departure board is C3's station card (a page card near the order board), not a mesh; it now lists 4 departures.

## Interchange and the Overland (M1 round B, builder B4)

- **Track:** `interchangeAdd` in "test yard layout" adds one straight edge (`ICH`): a dead end at (2, 20), east of the station and south of the passing siding, running east past the map edge (x = 60) to x = 140, so the Overland can stand off the map. Positions along it are s = x - 2. Speed limit 2.0 u/min (`CFG.LIM.interchange`). It is not joined to No. 1's track yet (coupling and moving set-out cars come in round C), and its edge has `fixed: true`: the build tool's `bStart` refuses track from its end or a switch on it ("That is the Overland's interchange track: it cannot be changed"), `bGeom` never snaps a plan onto its ends, and its ends get no brass rings. Staked jobs (B1) go through the same plan check, so they are refused too. `trainSendTo` onto it is refused with a reason.
- **Trains:** two more entries in `S.trains` (ids stay equal to the index): the Overland (`owner: 'overland'`, id 1) and its set-out cars (`owner: 'interchange'`, id 2, a train with no engine, possibly with no cars). `trainOff(tr)` (away, or no cars) makes `trainPoses` and `trainSegs` return nothing, so a train off the map is not drawn and blocks nothing; standing cars are an ordinary train to the walk grid, so they block walking like any train. Commands that drive a train (`useTrain`, `trainRun`, `trainStop`, `trainSendTo`) are refused for both with a `notYourTrain` event.
- **Visits** (`overlandTick` in "trains", step 3 of `simTick`, ticks only): at 06:00 and 18:00 the Overland appears just beyond the east edge (it comes in at that time and stands at the interchange about 30 game minutes later), pushing its cars ahead, and runs to the dead end or to the standing cars. With cars standing there it couples them (1.0 game minute). If any of them is empty or holds only goods for Outside it takes them: it pulls the whole string off the map, drops those cars (their goods are consumed as `soldOutside`; money comes in round C), and pushes the rest back in. Then it uncouples (0.5 game minutes) every car behind the engine that fits (the set-out cars must end by x = 48; the rest stay aboard, and while any stay aboard it brings no new delivery), and leaves east. Phases in `S.overland.phase`: away, in, couple, out, back, setout, leave. A phase of `off` (debug scenarios and checks only, never in play) stops the visits: B1's handbuild scenario and one part of `check-handbuild.js` use it, because they run past 06:00 and count every item in the game. A visit with no pick-up ends about 07:00; one with a pick-up about an hour later. Events `overlandArriving`, `overlandCoupled`, `overlandPickedUp`, `overlandSetOut`, `overlandLeft` show short messages.
- **Test delivery** (`OVERLAND_DELIVERY`, until import orders exist in round C): every morning a flatcar with 4 tie bundles, 2 rail bundles and a hardware crate (consignee CONSTRUCTION, id 0) and a boxcar with 2 spike kegs (CONSTRUCTION), 2 flour and a coffee for Willow Ford and tinned goods, lamp oil and clothing for the hub; every evening a boxcar with 2 flour (hub), beans, salt and the mail (Willow Ford) and whiskey (hub). Stock ids start at 100 (the Overland's engine) and count up in `S.overland.nextStock`.
- **Loading and unloading by hand** (end of "player", after the carrying code): a car is worked from beside it, at the door of a boxcar (middle of its side), the baggage door of a combine, or the nearest point of a flatcar's side (`carryCarDoor`), within 1.5u, 0.2 game minutes per item. `carryPick { id }` takes an item from a car, `carryPut { stock }` puts the top carried item into one, `useCar { stock }` walks to the door and gives `reachedCar`. All moves go through `itemMove`, so the cargo rules hold (no long bundles in a boxcar, long bundles by hand only, car capacities). Only standing cars that are not the Overland's own can be worked; a pick-up that finishes after the car has moved or been taken is refused.
- **Touch rule:** tap a set-out car: the player walks to its door and the car panel opens, listing what is in it (one button per item, 48 px high). Tap an item to take it; Put in loads the top carried item. The panel closes when the player walks more than 3u away, or the car goes. Tapping the Overland's engine or its cars while it is in shows "That is the Overland's train: its own crew drives it". No. 1 is unchanged: a tap opens its train panel (loading No. 1's own boxcar or combine works in the sim but has no button yet).
- **Drawing:** a flatcar model (`modelFlatcar`); the Overland's engine is the 4-4-0 with a blue-grey cab and wheels (`modelLoco('overland')`). The meshes are rebuilt when any train's cars change (`trainViewSig`). Items on a flatcar are drawn (long bundles along the deck, two across and two along per layer; crates at the deck ends) through the cargo instanced meshes, following the car every frame (`cargoFlatPoses`); a boxcar's load is inside and not drawn.
- **Saving:** schema 5. The 4 -> 5 step (`overlandMigrate`) adds the interchange edge to the saved track (old saves keep all their own track; a player's debug-built track lying where the interchange goes is not checked, it would simply overlap), adds the Overland (away) and empty set-out cars, and starts the visit state fresh. `overlandCheckSaveShape` checks it on load.

## Timetable, coupling, wood and water (M1 package 6, builder C3)

- **Where the code is:** coupling, uncoupling and engine state at the end of the trains part of "trains" (before the Overland); the new section "timetable" (after "trains"): stations, services, runs, line reservations, the run-around, person tasks at a train (uncouple, wood on the tender, water), the order board's data, saving and the debug scenario. The comment block at its top describes every field. `findRoute` (routes) takes an optional set of edges to avoid and returns its path and arrival facing. Page side: the order boards (`ttBuildBoards`, `ttDrawBoards`, end of "world rendering"), the panel's wood and water line, Timetable and Highball buttons and the order board card (`ttPanelUpdate`, `ttCardHud`, `ttOnEvent` in "HUD and panels"), and the train taps (`ttTap` in "input").
- **Vehicles:** `consist` is front to back; a vehicle turned round has `rev: true` (drawn turned by `trainPoses`). An engine's smokebox faces the train's front unless `rev`; `tenderFirst(tr, m)` replaces the old `m < 0` test, so routes and speeds handle an engine at either end. Our engines carry `fuel` and `water` (u of range left). Wood and water burn with the weight hauled: 1u per u run at 6 tons, so No. 1 with its two cars burns 72% and a light engine 50% (provisional). A tender holds 4 cords of 120u (30 miles); the tank 320u (20 miles), as section 7. Out of either, an engine creeps at yard speed.
- **Coupling:** a train moving by Forward or Back (mode `run`), or a route marked `couple` (Send to a standing car, or the run-around's last move), runs up to a standing cut (no engine, not the Overland's) and couples on contact: the cut's cars join in order along the track (turned ones get `rev`), the mover keeps its id, the cut's entry stays with no cars, and the train stands "Coupling up" for 1 game minute (`tr.cw`). Any other move stops 0.5u short of another train (`trainObstacle`); the Overland runs right up to its own set-out cars as before, and stops 0.5u short of anything else. **Uncoupling:** tap the gap between two vehicles: the player walks beside the joint and works 0.5 game minutes with the train standing (`uncouple { tr, at }`); the part with the engine keeps the id; the other becomes the interchange's cut entry (if on the interchange and that entry is empty), an empty `cut` entry, or a new one. A tap on a cut's car opens the car panel like a set-out car.
- **Stations:** `ttStations(S)` resolves station data onto the track. In the real start it reads C2's `stationsOf(T)` through `ttFromWorld` (stopping track = the first of `stops`; other tracks except the headshunt and interchange are alternates, which is how trains meet at Willow Ford's loop; water tower and wood stage = the world's buildings of those kinds near the station; run-around ends from `runAround`). The test yard has no stations of its own, so `TT_TEST_STATIONS` puts "Hub (test)" on the north main line and "Willow Ford (test)" on the south one (with the passing siding and water tower).
- **Services and dispatch:** two default services, Willow Ford Mixed morning (hub 08:00, Willow Ford 09:20 to 10:50, hub 12:50) and afternoon (13:30, 14:50 to 16:20, 18:20), timed from runs in the real start, with no engine on them: a new game is unchanged until the player taps Timetable in No. 1's panel (`ttAssign`). While a train is on the timetable it drives itself and Forward, Back, Stop and Send to are refused. A run starts 30 game minutes before its first departure and goes stop to stop. At a stop it waits for its time, the stop's actions (work: no goods for this station aboard and none for its later stops in the station's area; water: the train first moves (at most 40u) so a tender stands under the spout, then waits for the player to take water; wood: no room for another cord) and for wood and water for the next leg plus 2 miles. Highball (panel, at a stop) waves it off without its actions. Every move asks for a reservation of the blocks on its route; it is granted only if no other train holds or stands on any of them, released block by block as the tail clears (`S.tt.res`). Runs more than 6 game hours late are cancelled. Statuses say what a train waits for ("Waiting: take water at the tower", "Hold for orders: the line is not clear").
- **Run-around:** at a stop marked `turn: 'runaround'` with an engine that came in at the head of its train (one that came in pushing is already at the right end): the player uncouples the engine (status "Waiting: uncouple the engine to run around"); the engine runs clear beyond one end (stopping under the spout first if the stop takes water), back through the loop (track other trains stand on is avoided), and forward onto its cars, coupling on contact. It still faces the old way, so the next leg is tender first (60%, 2.4 u/min).
- **Wood and water by hand:** carry a cord of wood (a long bundle, by hand) and tap the engine: the player walks beside the tender and puts it on (0.2 game minutes; the item is consumed as `fuel`). Tap a water tower's spout with an engine's tender under it: the player works the spout 2 game minutes and the tank is full.
- **Order boards:** a post with a board and a lamp at each station: red (hold) or green while a timetable train is leaving on its reservation. Within 12u of a board a small card above it lists the next 3 departures with what each waits for (hidden where it would cover a button). Data: `ttBoard(S, id)`.
- **Saving:** schema 8 for now (C1's economy is 6, C2's world change 7; renumber at merge). The step adds `S.tt` (default services, no engine) and full wood and water to our engines. `ttCheckSaveShape` checks it on load.
- **Testing:** `?debug=1&scenario=timetable` (M0 test yard, 07:20, No. 1 on the timetable at the test hub, 6 cords at its wood stage). Hooks in `__railhead.tt`.
- **Known gaps:** no deadlock alert yet (two single-track stations each holding the other's train wait for ever); the player riding the train is not built, so in the real start the player walks 160u to Willow Ford; a player's cars left standing on the interchange beside the Overland's own cut are not known to the Overland.

### Provisional choices (timetable, for the designer)
- Coupling happens on contact at the end of a slow move, by the train crew, with no tap (the task asked for this); uncoupling needs the player at the joint. Section 7 says a person does both in the link-and-pin era.
- Times: uncouple 0.5 and couple 1.0 game minutes (section 7), water 2 game minutes, a cord onto the tender 0.2 (as any item).
- A tender holds 4 cords of 7.5 miles each; burn scales with weight (6 tons = 1u per u). With section 7's ranges taken flat, a round trip to Willow Ford with a run-around did not fit, so this keeps the doc's ranges for a normal train.
- The default services and their times; no engine on them in a new game (the player turns the timetable on); no run-around at the hub, so the afternoon train leaves the hub with the engine pushing.
- "Station work" is judged from the goods: none for the station left aboard, none waiting in the station's area for a later stop. Highball overrides.
- The order board is a post in the world plus a card shown within 12u (not a board readable when zoomed in).
- A timetable train refuses the player's driving commands until taken off the timetable; a player's Send to is refused through blocks a timetable train has reserved; a player's own moves take no reservation (they are stopped 0.5u short of other trains).
- Cordwood in normal play: nothing brings it yet (the test scenario puts 6 cords at the wood stage). It needs import orders (C1) or a starting stock at the wood stage.

## The real start (M1 package 9, builder C2)

- **Worlds.** A game is in one of two worlds, saved on its track: `S.track.world` is `'start'` (every new game) or `'yard'` (the M0 test yard: debug scenarios, `?world=yard`, and every save from before schema 7). `WORLDS` (section "starting world layout") holds per world: the track builder, the terrain grid, the walk grid, the map bounds (player, items, plans, camera), the flat areas, the hub boundary, the crowd area, and where the player and No. 1 start. `worldOf(T)` reads it from a track. `worldUse(T)` points the plain layout tables (`BLD_LAYOUT`, `BLD_BAYS`, `TOOL_PARK`, `CROWD.AREA`, the bounds `WB` used by `clampX`/`clampZ`) at that world; it is called at every entry point (`newState`, `simTick`, `walkGrid`, the plan check, `buildWorld`, every frame), so the tables always match the state in hand. The test yard is exactly as before: same track, buildings, bays and tool spots, and the same sim hash for the same commands (checked against the old build with the world field and schema number set aside).
- **Map (336u x 128u, 168 x 64 tiles; x -64 to 272, z -80 to 48).** Long and narrow because the line is: the hub (120u x 80u) at the west end, the interchange running off the west edge, and the 160u spur east to Willow Ford. The spur bends north in a gentle S (radius 60u, 30 degrees each way, a 39.85u straight between) so the map stays 128u deep and Willow Ford stands 24u clear of the east edge. Terrain: 6 x 2 chunks of 32 x 32 tiles (the last column 8 tiles wide), each culled on its own; the flat skirt beyond the edge is now one separate mesh (in both worlds), so the chunks keep small bounds. Usually 2 to 4 chunks are drawn. Held flat: 7u round every track sample, the hub boundary plus 2u (and the interchange beside it), and Willow Ford's station area.
- **Hub.** Boundary x -60 to 60, z -78 to 2 (60 x 40 tiles), drawn as a pale dashed line 1 cm up with survey stakes every 16u (in the merged buildings mesh). Track, west to east: the main track (z 0) from a dead end at x -40 (headshunt) through switch 0 (x 5, the interchange switch) and switch 1 (x 40, the platform-track switch) to the spur; the platform track (z -3.41) from switch 1 west past the platform to a dead end at x -36; the interchange (z +3.41, B4's fixed edge, 138u, node A at x -5.73 joined to switch 0's diverging leg, s = 58 about the map edge), outside the boundary. Buildings stand north of the platform track, laid out like the test yard's station moved 8u east (same distances from the track): the 20u platform (x -2 to 18), the depot (ticket window, telegraph and desk spots on the platform), a telegraph pole, the water tower (x 22.6), a wood stage (x 27.5), the freight shed with its dock and 4 bays (x -7.6), 4 lamps, and the hand truck and handcart spots east of the shed. No. 1 starts at the platform, engine east; the player on the platform by the depot. The build tool refuses plans outside the hub boundary ("Outside the hub boundary").
- **Willow Ford** (switch 2 at x 192, z -36): satellite kit with the main track and a run-around loop 3.41u south between switches 2 and 3 (40u apart), a 16u headshunt east of switch 3, a 16u x 2.4u platform north of the main track, the small depot behind it (its office bay on the platform's back edge), a water tower, 2 lamps, 4 cabins (scenery). Unstaffed.
- **STATIONS** (plain data, for C1, C3, C4): per station `id`, `name`, `town` (CARGO_TOWNS id), `staffed`, `depot` (layout id), `platforms`, `tracks` (named straight centre-line spans `{x0, z0, x1, z1}`; turn an end into `{e, s}` with `trackNearest`, since building a switch splits edges), `stops`, and at Willow Ford `runAround`. `buildingSpots()` gives the ticket, telegraph and desk spots of each depot as world points. Switch ids: 0 interchange, 1 platform track, 2 and 3 Willow Ford.
- **Walk grid**: one 0.5u grid over the whole map, 672 x 256 = 172,032 cells (the test yard keeps 240 x 240). Measured on the test machine: built in about 15 to 25 ms, 6.9 MB with the handcart grid; walking from the hub to Willow Ford (about 200u) costs 1.8 to 2 ms a tick on average. A search now stops after 60,000 cells (`WALK.MAXEXP`) and walks towards the nearest cell reached, so a goal cut off by a train cannot cost a whole-map search every tick (the test yard's largest area is 57,600 cells, so it never reaches the cap). Per-area grids were not needed.
- **Camera limits:** the point the camera looks at is kept inside the world's bounds; a pan past the edge is held there.
- **Saving:** schema 7 (6 is C1's economy; 8 is C3's timetable; 9 is C4's passengers; 10 is the towns, C5). The 6 -> 7 step marks an old save's track `world: 'yard'`, so it keeps the test yard's map, ground, buildings, bays and tool spots beside its own track, exactly as before, and its buildings cannot suddenly overlap its track. Only a new game gets the real start.
- **Debug:** `rh.scenario('start')` (a new real game) and `rh.scenario('willow')` (the same, with the player on Willow Ford's platform); the other scenarios are all in the test yard.

### Provisional choices for the designer (not settled by the design doc)
- The map size and shape (336u x 128u), the spur's S-bend north, and Willow Ford at the east end.
- The hub's track plan: the platform track is a stub off switch 1, so the hub has two switches (the interchange switch and the platform switch), not the one switch stand section 15 lists; the interchange joins the main track by its own switch, as asked. From the platform track to the interchange a train reverses on the main line.

- No telegraph shanty in the hub (the telegraph is in the depot); a telegraph pole stands beside the depot.
- Speed limits: hub and Willow Ford main tracks 4.0, platform track, loop, headshunts and connections 1.0 (yard).
- Sending No. 1 onto the interchange itself is still refused (B4's rule); it can go to the lead beside it. (Changed by C3, timetable: in the real start Send to onto the interchange is allowed, and Send to a set-out car couples it.)

## Draw calls

`__railhead.drawCalls` (and `rh.drawCalls`) counts a whole frame: the shadow pass plus the main pass. three.js clears its own counter after the shadow pass, so the page sets `renderer.info.autoReset = false` and calls `renderer.info.reset()` once per frame just before drawing. ## Technical choices to know about

- **Crowd speed is checked by update time, not frame rate:** the test machine draws in software (SwiftShader, no graphics chip), so its frame times say nothing about a phone. `check-people.js` limits the crowd's own update to 4 ms a frame and applies the 50 ms frame limit only on a real graphics chip.
- **Hills and walking:** the player, trains and the tap-to-walk ground plane are at height 0. The sim keeps the player on flat ground with `terrainFlatAt(track, x, z)` (pure math, no three.js; it works out the heights for the given track if needed). Hills are blocked cells in the walk grid, so tap to walk goes round them; press and hold slides along their foot. Crowd walkers never target or cross hills or buildings.
- **Crowd:** `?crowd=N` or `__railhead.setCrowd(n)` (default 0). Walkers are render-side only, with their own seeded random numbers, not in the save. One shader colours each person (skin, hair, top, lower, hat, vest packed per instance) and hides the shapes they lack (bit mask). Women: chunky or lanky with a skirt and a bonnet or bun; children: chunky at 0.7.

- **Shadow map:** 1024 pixels, not the design doc's 2048, to save phone memory and time.
- **Test yard geometry:** the switch's 30-degree diverging leg plus the 8u yard minimum radius and the 2u straight between reverse curves give a siding about 3.4u from the main line, wider than the 1.6u minimum.
- **Speeds:** the main loop is 4.0 u/min, diverging legs 1.5 u/min, and the siding and spur 1.0 u/min (yard speed).
- **Tender load:** the tender carries cordwood, not coal, because engines start on wood (section 2).
- **Switch points:** the point rails do not animate yet. The target disc shows the setting.
- **Send to:** a moving train only takes a route in the direction it is already going; otherwise "Stop the train first." Routes are compared by estimated time (tender-first runs at 60%).
- **Changing direction:** Forward or Back the other way while moving sets mode `turn`: the train brakes to a stop, then runs the new way. A braking train (modes `stop`, `turn`) still looks ahead and stops 0.5u short of a switch set against it or a dead end.
- **Route locks:** freed on arrival, Stop or a new command. A switch under a train stays locked because it is occupied (`occupiedSwitches`), not by the route.
- **Saving:** IndexedDB (gzip) a couple of seconds after a world-changing action and every 10 game minutes; on page hide or close also an uncompressed quick save in localStorage (`railhead-quicksave`). On start the save with the higher tick wins. A damaged save is kept as `broken-<time>` (IndexedDB) or `railhead-broken-<time>` (localStorage) and the game starts fresh with a console warning.
- **Terrain (piece 3a):** per world (see "The real start"); the test yard 64 x 64 tiles of 2u, 2 x 2 chunks of 32 x 32 tiles, one shared vertex-colour material (up to 4 draw calls), plus a flat skirt beyond the map edge (its own mesh since M1 package 9, 1 more draw call). Hills come from seeded value noise (up to about 5.5u). The ground is held at height 0 within 7u of every track corner sample and over x -25..25, z -20..24, and fades to flat at the map edge. The heights are worked out again from the current track each time `buildTerrain` runs. `terrainHeight(x, z)` uses the same triangles as the mesh. The terrain receives shadows but does not cast them.
- **Day and night (piece 3a):** `daylightAt(time)` gives the light for a game time (no three.js); `applyDaylight` applies it. Colours and sun elevations follow design-doc 17. The intensities are tuned rather than copied from the doc (provisional, for the designer's review): noon stays at the approved sun 0.8 and sky 0.5, while dawn, dusk and night are lifted so the scene stays readable on a phone. Sunrise and sunset: spring and autumn 06:00 to 19:00, summer 05:00 to 21:00, winter 07:00 to 17:00. Because the game starts at 05:00, the first minutes are in dawn twilight. `GLOW_MAT` glows from just before sunset until just after sunrise.

## Team mode (from 2026-11-01)

The designer asked for a team: the lead session hands out work to up to 6 workers (5 for M1), and an integrator merges it. Workers are helpers inside the lead session, never separate sessions (designer, 2026-11-01). Questions for the designer always go on an interactive survey page whose answers are saved in the page database (see CLAUDE.md).
The designer chose to review once, when all of M0 is done, instead of after every piece. The plans are recorded in `plans/m0-team-plan.md`.
Each builder owns one section of `index.html` (terrain, day and night, buildings, people (crowd), build tool, debug) and works on its own branch.
Each builder adds its own check file in `tests/` and one line to `tests/run-all.js`.
The integrator merges the branches into `ccr-59cb4c1f-rnscv9`, runs `npm test`, and fixes anything broken.
