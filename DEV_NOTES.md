# Railhead: developer notes

Read this first every session, together with `design-doc.md` (the design) and `CLAUDE.md` (how we work).
A fresh session should also read `plans/handover.md` if it exists.

## What the project is

Railhead (working title) is an isometric, low-poly railroad game set in 1866, built for phones first.
The whole game is one file, `index.html`, using three.js r128 loaded from cdnjs.
The full design is in `design-doc.md`. The original PDF it was converted from is kept in `docs/`.

## Platform decisions (2026-11-01)

These override the original design document wherever they disagree. Details are in `design-doc.md`, section 0 (decisions D1 to D11).

- Phones first, touch first, portrait and landscape. A computer with mouse and keyboard comes second.
- One HTML file, three.js r128 from cdnjs. There is no build step, no TypeScript and no Preact.
- The camera turns in 90-degree steps. The elevation is fixed at the true isometric angle.
- Avatar game: tap to walk there; press and hold walks towards the finger (D6, D7). Walking is part of M0 piece 1.
- Piece 1 uses the final low-poly models for the character, train, track and switch stands (D8).
- Size and speed targets are scaled down for phones (see design-doc section 0).

## How to test

1. Install the test tools once: `npm install`. This only fetches a copy of three.js r128 used by the tests.
2. Run every check: `npm test`. It must pass before every push.
3. Screenshots land in `test-output/`. That folder is not saved to git.

The checks serve the project on a local web address (saving in the browser needs one) and open `index.html` in Chromium through Playwright.
They use phone size (390 x 844 portrait, 844 x 390 landscape, with touch on) and fail on any console error.
Most checks open the page with `?paused`, so the game only advances when the check steps it.

Network note: the cloud test machine cannot reach cdnjs, because its network policy blocks it.
When that happens, the test script serves the identical three.js r128 file from `node_modules/three` instead.
The page itself still points at cdnjs.

Since D24 (the station rework) a new game starts in the **hub world** (`'hub'`, see "Station rework (D24)"). The checks written before it test the M1 real start (the hub and Willow Ford, see "The real start"): `tests/browser.js` opens the page with `world=start` unless the check's query names a world itself, so they keep testing what they tested. Checks written for the M0 test yard's layout open the page with `&world=yard` (a new game, and `__railhead.newState`, then use the test yard); `check-hubworld.js` and the D24 builders' checks open `&world=hub`. `__railhead.newState(seed)` makes a game in the page's world; inside the game `newState(seed)` with no world is still the real start (the debug scenarios written for it).
Since D25 (the prototype) a new game starts in the **prototype world** (`'proto'`, drawn as pixel art; see "Prototype (D25)"); `tests/browser.js` is unchanged (it still opens `world=start` unless the query names a world), so every older check keeps testing its world. The D25 checks open `&world=proto` (and `&world=` with no value for the page's default).

## Cargo (M1 package 2)

- **Items** (section "cargo (items and waybills)", after "trains"): `S.items` holds every freight item as columns indexed by item id (`waybill`, `where`, `alive`), plus `next` and the consumption log `used`. Ids are never reused. The API comment block at the top of the section lists the functions: `itemCreate`, `itemMove`, `itemCanMove`, `itemsAt`, `itemConsume`, `itemCheckConservation`. Other code must change items only through them. Each returns `{ ok, why }` and adds an event (`itemCreated`, `itemMoved`, `itemConsumed`, or `itemRefused` with the reason).
- **Places** (`where`): `CAR {stockId}`, `BAY {buildingId, bay}`, `CARRIED {actorId, carrier: HAND | HANDTRUCK | HANDCART, slot}`, `GROUND {x, z}` in hundredths, `STOCKPILE {jobId}`, `BUSINESS {businessId}`. The player's actor id is `'player'`. Cars now have stock ids (`consist[i].id`).
- **Limits**: a bay holds 8; by hand 1, hand truck 3, handcart 6; one way of carrying per actor at a time. Long bundles go by hand only, except cordwood, which may also go on the handcart (D13, 2026-11-02; never on the hand truck). The rule lives in one place, `CARGO_CART_LONG` / `cargoLongCarrierOk` at the top of `cargoRoomProblem`, which the conservation check reads too. A boxcar has 16 slots and a combine 8 (no long bundles). A flatcar takes long bundles, crates, pallets and machinery only (12 long or 8 crates: units of 2 and 3 out of 24). Bulk goods (logs, coal, ore) are not items.
- **Conservation**: `itemCheckConservation(S)` lists problems. Every item ever created is either alive in exactly one real place or logged once as consumed. Every place is within its limits.
- **Commodities**: `COMMODITIES` is the section 21 table (37 rows, prices in whole cents, null where it is not traded).
- **Destination tags**: `CARGO_TAGS` are WILLOW (W), HUB (T), HUBWH (H), RAILHEAD (R), OUTSIDE (O) and ANY (bays only). Each has a colour (colourblind-safe Okabe-Ito colours), a letter and a shape. `itemTag(waybill)` gives an item's tag.
- **Bays**: `BLD_BAYS` in "buildings" holds the bay positions as plain numbers, one bay in front of each of the freight shed's 4 doors. `S.bayTags.freightshed` holds the tags (default Willow Ford, Hub, Outside, Any since D4; before that the second bay was Hub warehouse, which saves from before cargo still get from the 1 -> 2 step, `CARGO_OLD_BAY_TAGS`). Change a tag with the command `{ t: 'setBayTag', b: 'freightshed', bay, tag }`. A non-matching bay is allowed and the move event says `mismatch: true`.
- **Drawing**: `itemPropShapes()` in "models" makes one low-poly shape per item type. "World rendering" draws them with one InstancedMesh per shape and one more for all the tag cards. `cargoDraw` in "drawing each frame" rebuilds the bays and the ground only when an item event happens (`cargoView.dirty`), when there is a new state, or when the camera turns. Carried items follow their actor every frame, through `cargoCarriedPose`, which builder W3 may replace. Items in a car, a stockpile or a business are not drawn. Code that changes items outside a tick calls `__railhead.cargo.redraw()`.
- **Testing**: `?debug=1`, then `rh.scenario('cargo')` or `?scenario=cargo`, gives 37 items (19 in bays, 15 on the ground, 2 in the boxcar, 1 in hand). A normal game starts with none; the Overland brings the first at 06:00 (see "Interchange and the Overland"). Test hooks are in `__railhead.cargo`.

### Provisional choices for the lead (not in the design doc)
- The tag letters and shapes are W Willow Ford (circle), T Hub town (square), H Hub warehouse (hexagon), R Railhead (triangle), O Outside (diamond) and A Any (ring). The colours are Okabe-Ito colours.
- A long bundle is refused on a handcart as well as on a hand truck. Section 9 says it goes "by hand" only. (Changed by D13: cordwood may go on the handcart.)
- Flatcar mixing uses units: a long bundle is 2 and a crate or pallet is 3, out of 24. Machinery is 9 units and is refused in bays and for carrying.

- **Wrong bay mark (D15, builder G):** an item in a bay whose tag does not match it (the move event's `mismatch`) gets a warning mark above its stack: a yellow triangle with a black edge and "!", standing upright facing the camera, 1.7 times a tag's size. It is the tag atlas's last cell (`CARGO_WARN_CELL`) drawn as an extra instance of the one tag mesh, so it costs no draw call. `cargoWarnMarks` makes the list (`cargoView.warn`) when the bays are rebuilt; `bayTagSet` now also marks the props for a redraw.

## Economy (M1 round C, builder C1)

- **Where the code is:** section "economy" (after "construction jobs"; pure sim). The comment block at its top lists `S.econ`, the API and the commands. Commands `useTelegraph`, `econOrder`, `contractAccept`, `contractDecline`, `creditDraw`, `creditRepay` in "commands"; `econTick` is step 8 of `simTick` (after the actors; `econTelBefore` notes a walk to the key before them). Page side: the telegraph panel (`telUi`, `telPanelUpdate`, `econOnEvent`) and the cash readout (`cashHud`) in "HUD and panels"; `econTelTap` in "input".
- **Money:** whole cents. `econPost` is the only thing that changes `S.econ.cash`; every change is a ledger entry `{ t, amount, category, counterparty, ref }` (categories in `ECON_CATEGORIES`). `econCheckMoney(S)` is the money rule (cash = starting cash + the ledger; credit owed = the credit entries; whole cents; known categories; time order), like `itemCheckConservation`.
- **Market:** `S.econ.market` buy and sell per commodity (section 21), with a per-commodity random walk (permille) moved every Monday 00:00 by up to 5% of base from the game's seeded numbers (`S.rng`, in commodity order), times the season factor, kept within 70% to 140% of base; 8 weeks of buy prices in `history`.
- **Telegraph key:** `econTelegraphKey()` is the hub depot's 'telegraph' use spot from `buildingSpots()` when the buildings section has it (C2), else worked out from the depot's layout entry (in front of the office bay window). Tap the bay window: `useTelegraph` walks there; on arrival `reachedTelegraph` opens the panel. Every economy command is refused (`econRefused`) unless the player stands within 3u of the key. The panel (car panel look, 48 px buttons) has three tabs: Order (- and + per good, Send order), Contracts (Accept, Decline; an open contract has a button to order what it still needs), Ledger (Borrow and Repay $500, the latest 12 entries). It closes beyond 3u. While paused, a panel button runs one tick so the money changes at once (as Lay track does).
- **Orders:** paid on order (`imports`). An order rides the first 06:00 or 18:00 Overland at least 6 game hours away. `overlandTick` calls `econLoadOverland` as the Overland comes in (unless it has cars held aboard): every order due, oldest first, while they fit in 6 cars; long bundles and machinery on flatcars, everything else in boxcars (first fit, `econPack`). Waybills: an order for a contract goes to its business with its `contractId`; ties, rails, spikes and hardware go to CONSTRUCTION 0; everything else to WAREHOUSE 0 (the hub warehouse). Events `orderPlaced`, `orderDelivered`.
- **The fixed test delivery** (`OVERLAND_DELIVERY`) now only comes when `S.overland.testDelivery` is set: the `interchange` debug scenario and `check-interchange.js` (`__railhead.interchange.withTestDelivery(st)`). Normal play brings only what was ordered.
- **Selling Outside:** goods consumed `soldOutside` on the Overland's pick-up are paid at the sell price (`econSoldOutside`, one `exports` entry per item; a part-used bundle pays for its pieces); `overlandPickedUp` carries `paid`.
- **Contracts:** `S.econ.contracts` (index = id), section 20 fields plus `period`, `owed`, `items`, `offered`. Businesses in `ECON_BUSINESSES`, which is the town section's `TOWN_BUSINESSES` (0 Hub General Store, 1 Willow Ford General Store, 2 Hub Developer's Yard, 3 Hub Saloon, 4 Hub Boarding House). A new game offers the section 21 first contracts (one commodity each: 6 flour and 4 beans by day 2, 8 lumber and 2 nails by day 4) and a standing one (2 coffee a week for 4 weeks to Willow Ford). `contractOffer(S, spec, ev)` adds offers (for C5). `contractDeliver(S, itemId, ev)` is for C5's local delivery: call it once the item is consumed with reason `business` (or while it is at `BUSINESS {businessId}`); it pays the contract its waybill names, or the oldest open one of that business for that commodity. Delivery contracts pay at once; standing contracts owe and pay on Saturday 18:00. Late: 10% a day off, up to 50%; reputation +2 on time, -4 late, -10 cancelled (5 days late). Offers not answered by their due time expire.
- **Credit line:** up to $5,000 from the Eastern investors, 1% a week charged on Monday 00:00; borrow and repay by telegraph. Cash may go to -$500 (orders beyond that are refused). **Lot fees:** `econLotFee` stub ($25 house, $60 business), called by nothing yet.
- **Cash on screen:** `#cash`, beside the speed buttons under the clock on a narrow phone, beside the clock when the screen is 600 px wide or more; red when negative.
- **Saving:** `S.econ` in the save; the migrate step gives an old save the starting cash and market, and the starting offers dated from its own day.

The job keeps its plan, its own copy of the new track (`geo`, never in `S.track`, so trains cannot use it), stakes every 2.5u, piece counts (a tie every 0.5u, a rail pair per 5u, 4 spikes per tie) and materials (per job, rounded up: tie bundles of 10, rail bundles of 4 rails, spike kegs of 80, and a hardware crate for a switch). With `?debug=1` the button stays Lay track (the parked instant build).
- **Materials on site:** a tie bundle, rail bundle, spike keg or hardware crate put down within 3u of a stake (carrying's put-down, or lying there when the job is staked) moves to `STOCKPILE {jobId}` through `itemMove`; `job.site` remembers where it was put down. A step opens a bundle or keg when it needs pieces: the item is consumed (`itemConsume`, reason `construction`) and its pieces go to `job.loose`. **Part-used bundles:** a waybill may carry `pieces` (fewer than a full bundle); they are made only when a job hands back pieces that do not fill a bundle (a cancel, or the round-up left over when a job finishes), and they open like full ones. So pieces are never lost, and the item conservation check holds unchanged.
- **Work:** `jobWork` walks the player beside the job (the side with more room, 0.9u out, 0.9u ahead of the next piece) and works while the next piece is within reach (1.5u), so the player walks every couple of units. Order, stretch by stretch (5u): that stretch's ties, its rail pair, then its spikes (`jobStepAt`). Times: tie 30, rail pair 60, spike 78 game seconds; the seconds left over from the tick that ends a step go into the next step, so the total is exact. Work stops when a material runs out (`jobStopped` with `missing` and a message), when the work cannot be reached, or when any other command replaces `P.use` / `P.act`. A switch job fits its hardware crate at its first rail pair.
- **Switches beside a standing train (D4):** `bStart` refuses a switch on a track only while a train moves on it ("A train is moving on that track") or stands over the switch's own 5u (its through leg, beside which the turnout's diverging leg runs) plus 1.5u at each end (`BUILD.SW_CLEAR`; "A train is standing where the switch would go"); until D4 any train anywhere on the edge refused it. When the switch splits the edge, `trackLayPlan` moves a train standing beyond the first cut onto the new piece it stands on (`bPlaceSwitch` returns the cuts and pieces), so it keeps its place exactly. Switches under trains stay locked as before (`occupiedSwitches`). So a siding can be staked off the platform track while No. 1 is home.
- **Finish and cancel:** after the last spike the plan is checked again and laid with `trackLayPlan` (same as `buildTrack`: the track index and walk grid caches are cleared, `trackBuilt` fires and the page redraws), unused items and loose pieces go back on the ground beside the job, the job is removed and `jobDone` fires. If the plan no longer fits (a train on the switch's track, say), the job stays finished-but-waiting and a later `jobWork` tries again. `jobCancel` returns every stockpile item to where it was put down and every placed or loose piece as items (whole bundles, plus one part-used one per material for a remainder).
- **Timing:** the handbuild scenario's 20u siding (with a switch) takes 1,884 ticks of work and walking: 251 game minutes, about 3.1 real minutes at 1x (4.2 at D17's slower clock). D12 said "about 5 real minutes", but its own step times give 232 game minutes (2.9 real minutes at the old clock) of work for 40 ties, 4 rail pairs and 160 spikes, so the step times were kept as approved.
- **Testing:** `?debug=1&scenario=handbuild` or `rh.scenario('handbuild')`: a 20u siding staked off the north main line (switch at x 18, facing west), with all 9 materials on site and the player beside its start. Then tap the stakes (or `rh.send({ t: 'jobWork', id: 0 })`). Test hooks in `__railhead.jobs`.
- **Taking materials back (D15, builder G):** a stockpile item can be picked up like any loose item (a tap on it, or `carryPick`): the player walks to where it was put down (`jobSiteSpot`), it leaves the stockpile, the job forgets its spot and says `jobTaken`, and the job's needs go up again. Put down within 3u of the stakes it is on site again. Opened bundles and placed ties, rails and spikes are not items, so they stay put. A tap near a stockpile item now picks it up rather than starting work (carrying's taps come first); tap the stakes away from the pile to work.
- **Not built yet:** fetching materials from the pile during work (the player works from the stockpile wherever it is within the 3u of the stakes). The Cancel button is on the job's sign label (drawing, below).

## How the game works (piece 1)

- **Simulation and drawing are kept apart.** The simulation advances in ticks of 8 game seconds, 7.5 ticks per real second at 1x (D17, 2026-11-02; was 10): one game minute is 1.0 real second, a game day 24 real minutes. 2x and 4x are 15 and 30 ticks a second; the debug warp's 32x is 240. `CFG.TICKS_PER_REAL_S` is the only place real time becomes game time: the main loop's tick accumulator, and the drawing-side game-minute figures of the walk (player, crowd and travellers) are worked out from it. Real-time things stay real time: the camera's follow lag and turn, telegram slide-ins, the roof fade, the idle breathing. The simulation itself does not read it, so ticks, results and save hashes are unchanged. Drawing reads the state and blends between the last two ticks.
- **Commands.** Every action is a command (`walkTo`, `walkDir`, `useSwitch`, `useTrain`, `throwSwitch`, `trainRun`, `trainStop`, `trainSendTo`), applied at the start of the next tick. Commands carry whole numbers only (positions in hundredths), so replays match exactly.
- **Track.** The track is a graph of nodes and edges. A position is `{e, s, d}`: edge, distance from node A, and facing (+1 towards B, -1 towards A). `trackWalk` follows the switches as set. `trackScan` looks ahead for the stopping point and speed limits. A train facing a switch set against it stops 0.5u before the switch's block, not at the switch point.
- **Trains.** A train stores only its front position. Each car's position is found by walking back along the track. This is exact because switches under a train are locked.
- **Routes.** A* over directed edges (length plus 20u per diverging switch), trying both directions of travel. Since D20 a route sets and locks no switch: it keeps the switches it needs and the train waits short of one set against it (see "Manual switches").
- **Player.** Tap to walk (`walkTo`, `useSwitch`, `useTrain`) follows a path from the walk grid (section "walk grid and path-finding", design-doc 11): one 0.5u grid over the whole map (the test yard 384 x 384 cells; the real start 1280 x 640 since D15, see "Scale (D15), sim side"). Blocked cells: building footprints grown by the player's radius (0.25u), any cell not flat at its corners, edge midpoints and centre (hills), and the cells under trains, which are stamped in at each query so the grid itself stays static. Costs: grass 1.4, platform and freight dock 1.0. While the player pushes the handcart, a second cached grid (made from the first on first use) also blocks the platform and the freight shed with its dock (`carryNoCartRects`, they have steps), so the path goes round them. The grid is cached per track and rebuilt only when the track changes (`walkGridSig`, and `buildTrack` clears it). A* is deterministic (whole-number costs, fixed neighbour order, ties by cell index), then the path is string-pulled (smoothed along clear straight lines). The path is never saved: it is worked out again every tick from the saved state (a memo keyed by start cell, target cell and train cells skips repeat work), so a moving train simply gives a new path round it, and a save loads to exactly the same walk with no new saved fields. A target inside a building, on a hill or in an area that cannot be reached is moved to the nearest cell that can be; the walk then ends there with the "Something is in the way" message (a train that stays in the way leaves the player standing beside it). A player inside a blocked cell (old save, teleport) first steps out to the nearest open cell. Press and hold (`walkDir`) is direct steering: a move into a train, hill or building tries its x-only and then z-only part, so the player slides along walls. A switch throw takes 0.5 game minutes at the stand, and only starts within 1.5u of it when the walk ended short. A tap on the train walks to within 1.5u of it (camera side preferred when both sides can be walked to straight; a side inside a building or on a hill gives way to the other side, reached round the train's end), then opens its panel.
- **Track and walking (provisional, for the lead):** design-doc 11 says track is impassable except at grade crossings and platform-end crossings. The M0 game lets the player cross track anywhere and throw switches from beside it, so for now track cells are walkable at the grass cost. Making track impassable needs crossings to exist first.
- **Path speed (test machine, software drawing, desktop CPU):** grid build about 3 ms; a typical path search (round the depot) about 0.01 ms; a long one across the yard about 2 ms (6,600 cells); the worst case (a goal that cannot be reached, so the whole connected area of 21,600 cells is searched, as when a train cuts it off) about 5 ms. A sim tick while walking about 0.2 ms. The worst case can repeat every tick only while a train keeps a target cut off.
- **Models.** Built in code from the style test page shapes. Each vehicle or body part is merged into one mesh with vertex colours and one shared material.
- **Build tool (piece 2, M0 instant build).** The Build button (top right, or the B key) turns on build mode: one finger draws track instead of walking; pinch and two-finger pan still work. A drag that starts on a track end (brass ring) continues it; one that starts on a straight places a switch there (5u through leg, radius 10u 30-degree diverging leg, on the side the finger moves to) and carries on from the diverging leg; one that starts on open ground starts a free piece heading the first drag direction (snapped to 15 degrees). The plan follows section 6: straight within 1 degree, else arc then straight (largest radius, 15-degree straights, nearby straight track's heading first, ends snapped to 1.6u parallel offsets); an end within 0.5u of a track end joins it with a straight, arc, arc + straight, straight + arc or S-curve. The ghost is green (valid), amber (ground more than 0.3u off the bed: needs earthwork) or red with the reason in the label. Red covers: radius by class, reverse curves without the straight, closer than 1.6u to other track or crossing it, building clearance (if `buildingFootprints()` exists), off the map, a train on the track, too little straight for a switch, and anything `trackValidate` finds. On release, Lay track / Cancel appear; Lay track sends `{t:'buildTrack', ...}` (whole numbers only), which re-checks and applies or refuses with an event. If the game is paused, Lay track runs one tick so the track appears at once. Splitting an edge keeps its id (it is shortened) and appends the rest.
- **Instant build parked behind `?debug=1` (D10).** The designer cut the M0 instant build; its code stays but only works with `?debug=1`. Without it the Build button and planning (ghost, green/amber/red, label) still work, but after release the button beside Cancel is Stake it (a construction job, see "Construction jobs" below) instead of Lay track. `send()` (the page's command intake, so also `__railhead.send` and `rh.send`) asks `buildIntakeRefusal()` in the build tool section first: without `?debug=1` a `buildTrack` command never reaches the queue and a `buildRefused` event (with `debugOnly: true`, recorded in `buildTool.refused`) shows "Cannot lay that track: instant track laying is switched off ...". Why there: the sim tick must never read page flags, or the same commands could give different results depending on the address; gating at the door where the page hands commands to the sim keeps `simTick`/`simRun` identical with debug on or off (the sim-only checks still build track through `simTick` directly). `buildTool.instant` says which mode the page is in.
- **Test hooks.** `window.__railhead` gives access to the state, `step(n)`, `send(cmd)`, `newState`, `simRun`, `stateHash`, `exportSave`/`importSave` and `toScreen`.

## Debug tools (`?debug=1`)

- Off unless the address has `?debug=1`: no extra page elements, meshes or work per frame.
- A DBG button (bottom right, above Centre) opens a bar: overlay toggles (Blocks, Locks, Routes, Path) and 8x, 16x, 32x, 1x speeds. The train panel covers the bar when open.
- Overlays: blocks coloured per block (occupied red, reserved by a route orange); switch markers (green free, orange locked by a route, red occupied) with a stub along the set leg; each train's remaining route (cyan); the player's target and path (pink: the smoothed walk-grid path for a tap to walk, with a small diamond where the walk really ends if that is short of the target; a straight line for press and hold). One merged mesh each (one draw call each), drawn on top without depth test, rebuilt only when what they show changes (checked every 3 frames).
- Console `window.rh`: `send(cmd)`, `state`, `hash()`, `step(n)`, `setTime(seconds since 05:00 on day 1)`, `warp(0..32)`, `teleport(x, z)`, `scenario('yard' | 'siding' | 'spur' | 'cargo' | 'interchange' | 'handbuild' | 'start' | 'willow')` (interchange: 05:50 on day 1, the player beside the interchange's dead end), `overlay(name, on)`, `drawCalls`, `help()`.

- Warp above 4x runs up to 640 ticks of backlog, time-boxed to about 8 ms per frame; the rest carries over. It only runs more ticks, so results stay the same.

## Carrying (M1 package 1)

- **Where the code is:** the end of the "player" section (`carryActorTick` and the `carry*` functions, after `playerTick`), the commands `carryPick`, `carryPut` and `carryTool` in "commands", `modelHandTruck`, `modelHandcart` and `TOOL_STACK` in "models", `carryDraw` and `carryItemPose` at the end of "world rendering", the readout (`carryHud`) in "HUD and panels", and `carryTap` in "input". The item store itself is the cargo section's (builder W2).
- **How it runs:** `carryActorTick` replaces the direct `playerTick` call in `simTick`. A pick-up or put-down in progress (`P.act.k` is `pick` or `put`) is counted down there; otherwise `playerTick` walks as before, and afterwards the carry code notices arriving at an item, bay or tool spot (`P.use.k` is `pick`, `put` or `tool`) and starts the 0.2-minute action if within 1.5u. The walking code is untouched, so path-finding can change underneath it.
- **Cordwood on the handcart (D13, builder D6):** up to 6 cords; other long bundles (ties, rails, lumber, poles) are refused ("only cordwood goes on the handcart"), and every long bundle on the hand truck. Cords go from the handcart onto the tender one at a time (`fuelTender` takes the top carried cord, as by hand); pushing the handcart, the walk to the tender goes to the side away from the platform (`ttWalkBeside`). Drawn lying along the handcart's bed, two side by side, up to three layers (`carryItemPose` with the item id).
- **Carried items** are at `{ kind: 'CARRIED', actorId: 'player', carrier, slot }`. `carrier` is `HAND`, `HANDTRUCK` or `HANDCART`, from the tool pushed (`S.player.tool`, null or an index into `S.tools`). Slot 0 fills first; Put down takes the top slot. Taking a tool moves a hand-held item onto it (refused for a long bundle). A loaded tool cannot be left. Tools are taken and left only at their parking spots (`TOOL_PARK`, east of the freight shed, on the side away from the track), saved in `S.tools`.
- **Handcart:** may not go on the platform or the freight shed and its dock (`carryNoCartRects`, from the building layout plus 0.2u); a step that would enter is undone and the walk stops with a message. It can still put items into the bays from the track side of the dock (within reach). Known gap: the walk grid does not know about the handcart, and the platform and dock are its cheapest cells, so a path may lead onto them and the handcart stops at the edge; the walk grid should block those cells while a handcart is pushed (a follow-up for the path-finding owner).
- **Taps:** a tool spot takes or leaves that tool; an item picks it up if there is room; while carrying, a bay or the dock puts the top item in that bay (dock taps go to the nearest bay, as the cargo section draws ground items at ground height); by hand, the ground puts the item there. With a tool, a ground tap just walks; the readout's Put down button (or F) puts an item down beside the player.
- **Drawing:** the pushed tool stands ahead of the player (`CARRY_PUSH`); the hand truck leans back round its axle. Arms are forward 70 degrees carrying by hand, 45 degrees pushing, and dip during an action. A brass progress ring above the head shows any timed action, switch throws included.
- **Feet on the decks (D15, builder F):** `bldStandY(x, z)` (buildings section, after `buildingFootprints`) is the one height lookup for people: the deck top (`BLD_PLATFORM_TOP`) on the flush footprints (the platforms and the freight dock, cached per `BLD_LAYOUT`), the ground elsewhere, eased over `BLD_STEP_R` (0.12u) either side of a deck's edge so walking on or off is a short smooth step. It follows the layout's numbers, so scaling or a new deck height needs no change here. The player, the pushed or parked tool, the item in hand, the tie on the shoulder, the progress ring and travellers (`paxStandY`) all use it; taps for walking and putting down use `deckGroundAt` (the deck's top where the ray meets it inside a deck, else the ground), and the tap marker sits 0.05u above that surface. Drawing only: the sim has no height, so saves and the state hash are unchanged.

## Passengers (M1 package 5, builder C4)

- **Where the code is:** section "passengers" (after "player", before "sim tick"; pure sim): `PAX` (all the numbers), the store `S.pax` (its comment block lists every field), stations (`paxStations`), the queue, ticket sales, boarding, the commands' code and `paxDebugScenario`. `paxTick` is step 8 of `simTick`. Commands `staffWindow { st }` and `leaveWindow` in "commands". Drawing: the end of "people (crowd)" (`paxView`, `paxLook`, `paxDraw`, called from `render()` after `updateCrowd`). Page side: `paxTap` in "input" (a tap within 34 px of a ticket window), and in "HUD and panels" the staffing readout (`#paxDesk`, with Leave) and the window's "Tickets (n)" button (`.paxWin`), in `paxHud`.
- **Stations:** read from data, never hard-coded. With C2's station table (`stationsOf(T)`) each station names its platform and depot, and the depot's `ticket` use spot (`buildingSpots()`) is where the player stands to sell; the window is 0.67u behind it. Without it (the M0 test yard, which has no table) each platform footprint is a station (the first is the hub) with its nearest depot, and the window is on the depot's track-side wall 0.35 of its width from its middle (where the recipe draws it). Cached per world. A station's edges are 0.8u past its platform's ends.
- **Travellers:** whole-number positions (hundredths), saved with their path (the way worked out on the walk grid, round buildings, hills and standing trains, when they set off somewhere). They walk 27 hundredths a tick (2.0 u per game minute). A step into a train waits; after 4 ticks the way is worked out again. States: `queue` (in line), `wait` (ticketed, on the platform), `board` (to a door), `aboard` (in a car, not drawn), `off` and `leave` (walking to the station's edge, then gone). Their own random numbers (`S.pax.rng`), so other systems are untouched.
- **Rates:** hub one traveller every 20 game minutes on average, Willow Ford every 45 (each gap 0.5 to 1.5 times that, in whole ticks), only 06:00 to 21:00, appearing at a random edge of their station and wanting the other station. At most 48 waiting per station (queue, platform and walking to a door; 24 until D20, when nobody gives up any more); while that many wait, no more come (the queue's 48 places fill about 2.5 rows along the back of the platform). Plus 1 to 3 off each Overland visit (when it sets out its cars), appearing beside its engine and walking to the hub's queue, for Willow Ford.
- **Ticket window:** tap the window (or its "Tickets (n)" button, shown while people queue): the player walks to the staff spot; arriving there staffs it (`deskStaffed`), facing the queue. While staffed and the first in line is within 1.5u, a ticket takes 30 game seconds (counted in 8-second ticks with the remainder kept, so the average is exact). Any walk or action, or Leave, stops it. Fare: 4 cents a mile, at least 10 cents; the hub to Willow Ford is 10 miles (160u, section 15) so 40 cents. Each fare is posted with C1's `econPost(S, cents, 'fares', 'Ticket, Hub to Willow Ford', { kind: 'TICKET', id }, ev)`: one ledger entry per ticket, and the cash goes up. Counts per station in `S.pax.sold` and `S.pax.cents`.
- **The queue:** places 0.6u apart along the platform from beside the staff spot, then back in a second row, on open walk-grid cells inside the platform (24 places).
- **Unstaffed stations (D13, builder D6):** a station with `staffed: false` in `STATIONS` (Willow Ford; `paxUnstaffed`) has nobody selling tickets unless the player stands at its window. Travellers still come and wait in line by the window (and still go home after 60 game minutes with no train). When a passenger car of a train that serves them stands at the platform, those in line board too, after the ticketed ones, without a ticket. Stepping off, each pays the fare (`paxFare` of the two stations, 40 cents): one ledger entry through `econPost` (category `fares`, counterparty "Fare paid on arrival, Willow Ford to Hub", ref `{ kind: 'FARE', id }`) and an event `farePaid`. A car that moves off sends them back into the line. The hub is staffed: without a ticket nobody boards there, even while the player is away from the window. Fares paid on arrival are not counted in `S.pax.sold`/`cents` (the ledger has them), so the save shape is unchanged. The test yard has no station table, so its stations count as staffed.
- **Giving up (parked since D20 (3), "people should wait in line as long as needed"):** nobody leaves the ticket line (`PAX.GIVE_UP_S` is 0; the M1 rule, home after 60 game minutes with the count `S.pax.rep[station]` going up, stays in the code switched off, and its toast with it). `S.pax.rep` stays in the save at 0. Willow Ford still lets those in line board without a ticket and pay on arrival.
- **Boarding:** a passenger car (`PAX.SEATS`: combine 12, coach 30) of a train of ours standing still (not running, routed or turning) with its centre beside the platform's track edge. Its doors (`PAX.DOORS`: the combine's one passenger door at its passenger end, 1.25u from its centre; a coach two) have boarding spots 1.3u out on the platform; a door up to 0.5u past the platform's end still serves it, its spot pulled 0.3u inside the end (No. 1 stopped mid-span at Willow Ford leaves the combine's door just past the 16u platform). At each door, one traveller every 6 game seconds (0.1 minutes): those for this station step off first, then ticketed travellers board in id order, never past the seats. A train that moves off sends the walkers back to waiting. The cars a timetable train's engine is running round stand at the platform as part of that train (D7), so travellers step off and board them meanwhile. A timetable train waits at the platform for its travellers (see "Platform work" in the timetable section). Which trains take travellers (`paxTrainServes`): a train on the timetable (C3's `S.tt` services) only while its run is at this station and calls at the traveller's station later on; a train off the timetable (driven by the player) always.
- **Departure board:** one board per station, C3's station card (`ttCardHud`, shown while the player is within 12u of the station's order board), now listing the next 4 departures (`ttBoard` showed 3; changed by C4). For other code, `stationDepartures(S, stationId)` gives the next 4 departures as data `[{ time, train, to, platform, state }]` from C3's services (`S.tt.services`, days and stop times), soonest first within the next 24 game hours; a service that already left today gives tomorrow's run; state is On time, Late or No engine. Platform is always 1.
- **Drawing:** travellers use the crowd's 15 instanced meshes (room for 96 per kit after the walkers), so they add no draw calls when a crowd is shown, and at most the crowd's 30 (with shadows) when it is not. Looks from their id (`crowdDescribe`, never railroad staff or a conductor). On a platform or the dock they stand on its top. In line they face the window; waiting, the track.

## Timetable, coupling, wood and water (M1 package 6, builder C3)

- **Where the code is:** coupling, uncoupling and engine state at the end of the trains part of "trains" (before the Overland); the new section "timetable" (after "trains"): stations, services, runs, line reservations, the run-around, person tasks at a train (uncouple, wood on the tender, water), the order board's data, saving and the debug scenario. The comment block at its top describes every field. `findRoute` (routes) takes an optional set of edges to avoid and returns its path and arrival facing. Page side: the order boards (`ttBuildBoards`, `ttDrawBoards`, end of "world rendering"), the panel's wood and water line, Timetable and Highball buttons and the order board card (`ttPanelUpdate`, `ttCardHud`, `ttOnEvent` in "HUD and panels"), and the train taps (`ttTap` in "input").
- **Vehicles:** `consist` is front to back; a vehicle turned round has `rev: true` (drawn turned by `trainPoses`). An engine's smokebox faces the train's front unless `rev`; `tenderFirst(tr, m)` replaces the old `m < 0` test, so routes and speeds handle an engine at either end. Our engines carry `fuel` and `water` (u of range left). Wood and water burn with the weight hauled: 1u per u run at 6 tons, so No. 1 with its two cars burns 72% and a light engine 50% (provisional). A tender holds 4 cords of 120u (30 miles); the tank 320u (20 miles), as section 7. Out of either, an engine creeps at yard speed.
- **Coupling:** a train moving by Forward or Back (mode `run`), or a route marked `couple` (Send to a standing car, or the run-around's last move), runs up to a standing cut (no engine, not the Overland's) and couples on contact: the cut's cars join in order along the track (turned ones get `rev`), the mover keeps its id, the cut's entry stays with no cars, and the train stands "Coupling up" for 1 game minute (`tr.cw`). Any other move stops 0.5u short of another train (`trainObstacle`); the Overland runs right up to its own set-out cars as before, and stops 0.5u short of anything else. **Uncoupling:** tap the gap between two vehicles: the player walks beside the joint and works 0.5 game minutes with the train standing (`uncouple { tr, at }`); the part with the engine keeps the id; the other becomes the interchange's cut entry (if on the interchange and that entry is empty), an empty `cut` entry, or a new one. A tap on a cut's car opens the car panel like a set-out car.
- **Stations:** `ttStations(S)` resolves station data onto the track. In the real start it reads C2's `stationsOf(T)` through `ttFromWorld` (stopping track = the first of `stops`; other tracks except the headshunt and interchange are alternates, which is how trains meet at Willow Ford's loop; water tower and wood stage = the world's buildings of those kinds near the station; run-around ends from `runAround`). The test yard has no stations of its own, so `TT_TEST_STATIONS` puts "Hub (test)" on the north main line and "Willow Ford (test)" on the south one (with the passing siding and water tower).
- **Stopping tracks across joints (D15, builder G):** a station's stopping track (`trk`, and each of `trks`) is resolved by `ttSpanOf` into pieces: `{ segs: [[edge, s0, s1]], len, ends: [{ e, s, d }], mid }` (plus the old `e, s0, s1`, the longest piece). On one edge it is exactly the old span. When a switch has been built inside it (which splits its edge), the span is the shortest way between its two ends, kept only if it is about as long as the straight line between them (so it never runs onto a diverging leg or round a loop). `ttPlanStop`, `ttAtTrack`, `ttLegU`, `ttWoodNeedU`, the move back to the platform and `ttDebugScenario` all read the pieces, so a switch inside a platform no longer cancels that station's runs. In the real start the platforms and the parallel tracks leave no room for such a switch; in the M0 test yard the hub's stopping track has room.
- **Services and dispatch:** two default services, Willow Ford Mixed morning (hub 08:00, Willow Ford 09:30 to 10:50, hub 13:00) and afternoon (14:00, 15:30 to 16:20, 18:30), timed from runs in the real start. Since D21 a new game in the real start has No. 1 on both (`newState` sets `train: 0` after `ttNewState`; the test yard keeps none; loading a save never comes through `newState`, so saves keep what they have); the player takes her off or puts her on with Timetable in her panel or the office's Timetable tab (`ttAssign`, optionally per service). (Until D21 they started with no engine.) (Until D4: Willow Ford 09:20, hub 12:50; afternoon 13:30, 14:50 to 16:20, 18:20, and no water on the way in; saves from before the timetable still get those, `ttDefaultServices(true)`; later saves keep the services they have.) While a train is on the timetable it drives itself and Forward, Back, Stop and Send to are refused. A run starts 60 game minutes before its first departure (`TT.START_EARLY_S`, 30 until D4) and goes stop to stop. At a stop it waits for its time, the stop's actions (work: no goods for this station aboard and none for its later stops in the station's area, which at the hub takes in the freight shed's bays; water: the train first moves (at most 40u) so a tender stands under the spout, then waits for the player to take water, and a tank short by no more than a 40u move burns counts as full; wood: enough for the route to the next station with a wood stage (from where the train stands, the legs after, twice each run-around, plus 2 miles), or no room for another cord, and once met at a stop it stays met there, so the short move to the spout cannot bring it back) and for wood and water for the next leg plus 2 miles.
- **Water on the way in (D4):** a run's last stop with `water` in its acts (both default services' return to the hub) does not take water at the stop: leaving the stop before it, the train is routed to the station's spout first (`ttPlanSpout` with no distance limit), stops with its tender under it and waits up to 10 game minutes (`TT.IN_WATER_S`) for the player to take water (or, once watered, while the player carries a cord of wood within 12u of a tender with room, so wood from the wood stage beside the tower can go on there too); working at the train (water or wood, or walking up to it from within 6u) restarts the 10 minutes (`ttCrewAt`). Someone standing by with a cord does not hold it beyond that. Then it runs on to the platform. The next departure then needs no move: it leaves from the platform (where passengers can board) with a full tank. If the player missed it, the departing run moves to the spout as before, now with about 35 minutes in hand (60 minutes early, about 25 minutes' crawl). A run starting with its train already under the stop's spout counts as at the stop. Highball (panel, at a stop) waves it off without its actions. Every move asks for a reservation of the blocks on its route; it is granted only if no other train holds or stands on any of them, released block by block as the tail clears (`S.tt.res`). Runs more than 6 game hours late are cancelled. Statuses say what a train waits for ("Waiting: take water at the tower", "Hold for orders: the line is not clear").
- **Platform work (D7):** at every timetabled stop a train with a passenger car does its platform work at the platform. It stands on the stopping track at least 5 game minutes (`TT.DWELL_S`) before it moves on (to the spout or away), and longer while a traveller for this station is still aboard one of its cars beside the platform (they always step off here) or a traveller walks up to board (that part up to 15 minutes after it came in, `TT.PLAT_MAX_S`); status "Waiting: passengers stepping off and boarding" (`ttPlatformHold`, `run.pT` = when it came to stand there). Then it moves to the spout for water if it still needs it. After water at a spout off the stopping track (Willow Ford's, beyond the platform's east end, when the engine came in pushing and needs no run-around) it stops at the platform again on its way out, if the platform is on its way (the departure route runs over the stopping track) and at least 15 minutes (`TT.BACK_S`) are left before the departure (status "Running back to the platform", tried once per stop, `run.back`), so it leaves from the platform and travellers who came meanwhile board too. A hub departure that had to move to the spout (water missed on the way in) still leaves from there: the platform is behind it. During a run-around the cars left standing at the platform count as the train for travellers (`paxCarsAt`). Highball skips all of this. No save change: `pT` and `back` are new optional fields of a run (an old save mid-stop just starts the dwell when loaded).
- **Run-around:** at a stop marked `turn: 'runaround'` with an engine that came in at the head of its train (one that came in pushing is already at the right end): the player uncouples the engine (status "Waiting: uncouple the engine to run around"); the engine runs clear beyond one end (stopping under the spout first if the stop takes water), back through the loop (track other trains stand on is avoided), and forward onto its cars, coupling on contact. It still faces the old way, so the next leg is tender first (60%, 2.4 u/min).
- **Wood and water by hand:** carry a cord of wood (a long bundle, by hand) and tap the engine: the player walks beside the tender and puts it on (0.2 game minutes; the item is consumed as `fuel`). Tap a water tower's spout with an engine's tender under it: the player works the spout 2 game minutes and the tank is full.
- **Order boards:** a post with a board and a lamp at each station: red (hold) or green while a timetable train is leaving on its reservation. Within 12u of a board a small card above it lists the next 3 departures with what each waits for (hidden where it would cover a button). Data: `ttBoard(S, id)`.
- **Saving:** schema 8 for now (C1's economy is 6, C2's world change 7; renumber at merge). The step adds `S.tt` (default services, no engine) and full wood and water to our engines. `ttCheckSaveShape` checks it on load.
- **Testing:** `?debug=1&scenario=timetable` (M0 test yard, 07:20, No. 1 on the timetable at the test hub, 6 cords at its wood stage). Hooks in `__railhead.tt`.
- **Known gaps:** no deadlock alert yet (two single-track stations each holding the other's train wait for ever); (since D13 the player can ride the train, see "Riding our own train"); a player's cars left standing on the interchange beside the Overland's own cut are not known to the Overland.

## The real start (M1 package 9, builder C2)

- **Worlds.** A game is in one of two worlds, saved on its track: `S.track.world` is `'start'` (every new game) or `'yard'` (the M0 test yard: debug scenarios, `?world=yard`, and every save from before schema 7). `WORLDS` (section "starting world layout") holds per world: the track builder, the terrain grid, the walk grid, the map bounds (player, items, plans, camera), the flat areas, the hub boundary, the crowd area, and where the player and No. 1 start. `worldOf(T)` reads it from a track. `worldUse(T)` points the plain layout tables (`BLD_LAYOUT`, `BLD_BAYS`, `TOOL_PARK`, `CROWD.AREA`, the bounds `WB` used by `clampX`/`clampZ`) at that world; it is called at every entry point (`newState`, `simTick`, `walkGrid`, the plan check, `buildWorld`, every frame), so the tables always match the state in hand. ## The walk (D20, builder AN; first built 2026-11-02 by builder W)

**Speeds (D20, game units per game minute, which is u a real second at 1x):** the player walks 2.0 (`CFG.WALK`, was 2.8); there is no running at all (`CFG.RUN`, the Shift key and the player's `run` flag are gone; a `walkDir` or `walkTo` sent with `run` set walks; an old save keeps its unused `run` flag, so its load hash is unchanged); pushing the hand truck or handcart 1.8 (`CFG.TOOL_WALK`); crowd walkers 1.8 (`CROWD.WALK`, was 2.5) and travellers 1.8 (`PAX.STEP` 24, was 27). The bot (`tests/m1-bot.js`) never ran, so nothing there changed.

**The player's model** (`modelChunky`, models section) is the same shapes and colours as before, cut at the knees and elbows, and is now ONE skinned mesh (`THREE.SkinnedMesh`, `PLAYER_MAT` with skinning on): each shape is bound whole to one bone (no blending, so it stays flat-shaded low-poly). Bones in `userData`: `hips` (pelvis) > `legL/R` (thighs) > `shinL/R`; `footL/R` (boots, placed where the walk puts the feet); `upper` (torso) > `head`, `armL/R` > `foreL/R`; markers `handL/R` (fists) and `soleL/R`. Rig sizes in `PLAYER_RIG` (thigh 0.16, shin 0.125, ankle 0.055). The maul hangs from `handR` (its handle was tilted the wrong way off its head, fixed). **Draw calls: the player costs 2 (was 10).**

**The walk** (`GAIT`, drawing only; the sim never reads it): a step cycle `g.ph` moves on by the distance drawn over the stride, so planted feet stay put. Each foot is down for half its cycle (`GAIT.F`); in the swing it lifts early (heel up behind, so the knee bends), swings through and lands toes up. `gaitLegs` is two-bone IK from each hip joint (after the pelvis's drop, twist and roll) to its foot target: thigh pitch and tilt, knee bend, and a stretch over 1 only at the ends of a long stride (up to 1.15 at the walk; the legs are 0.34 long and a step is 0.49u). The hips drop at each heel strike (0.05u, twice a stride), twist with the forward leg and roll down on the swing side; the shoulders twist the other way, the torso sways over the standing foot, the arms swing against the legs with the elbows bending more forward, the head stays level. Standing: a slow weight shift (`GAIT.IDLE_HZ`, one knee eases) and breathing. Starts and stops blend in and out (`g.sw`).
- **Cadence:** stride `GAIT.STRIDE_K` x hip height x the square root of speed over 2.0 (shorter for slower people, x 0.78 pushing): walking 0.99u, 2.03 cycles = **4.06 steps a real second** at 1x; pushing 0.73u, 4.9 steps; crowd chunky walkers at 1.8 about 3.9 steps.
- **Poses** (all on `u.pose`, put on the model once a frame by `gaitApplyPlayer` after the walk, carry and work layers in `render`): carrying by hand (`carryDraw`), both hands at the item's sides, shoulders back, and the item is drawn between the hands (`cargoCarriedPose`); pushing, a lean into the handles with the arms nearly straight to the grips (`CARRY_PUSH` now holds the tool farther out and the arm angles per tool); picking up and putting down bend the hips and knees; hand-building (`jobPose`, `WORK_POSE.blow`): the tie on the right shoulder then set down bending at hips and knees, the rail pair held low then dropped, maul blows with wind-up overhead, a fast strike folding at the hips and knees (impact at 0.72 of a blow, when the spike drops) and follow-through, feet set apart; throwing a switch (`throwPose`): reach, a two-handed pull back sitting into the legs, let go.
- **Crowd and travellers** (people section): the same `GAIT` and `gaitLegs`, still 15 instanced meshes (30 draw calls with shadows, unchanged). The knee (legs) and elbow (arms) angles ride in each instance matrix's spare slot (column 0, w); `CROWD_BEGIN` (vertex shader, colour and shadow passes) turns the shapes added after `CrowdPart.bend(y)` about that joint and clears the slot before the matrix is used. Seated travellers in the cutaway sit with the knees bent and feet on the floor by the same IK.
- **Hooks:** `__railhead.gait` has `GAIT`, `PLAYER_RIG`, `gaitPose`, `gaitLegs`, `gaitApplyPlayer`, `throwPose`, `WORK_POSE`, `maul`, and `posePreview` (a function run on the pose each frame, for checks and screenshots only).

## Technical choices to know about

- **Crowd speed is checked by update time, not frame rate:** the test machine draws in software (SwiftShader, no graphics chip), so its frame times say nothing about a phone. `check-people.js` limits the crowd's own update to 4 ms a frame and applies the 50 ms frame limit only on a real graphics chip.
- **Hills and walking:** the player, trains and the tap-to-walk ground plane are at height 0. The sim keeps the player on flat ground with `terrainFlatAt(track, x, z)` (pure math, no three.js; it works out the heights for the given track if needed). Hills are blocked cells in the walk grid, so tap to walk goes round them; press and hold slides along their foot. Crowd walkers never target or cross hills or buildings.
- **Crowd:** `?crowd=N` or `__railhead.setCrowd(n)` (default 0). Walkers are render-side only, with their own seeded random numbers, not in the save. One shader colours each person (skin, hair, top, lower, hat, vest packed per instance) and hides the shapes they lack (bit mask). Women: chunky or lanky with a skirt and a bonnet or bun; children: chunky at 0.7.

- **Shadow map:** 1024 pixels, not the design doc's 2048, to save phone memory and time.
- **Test yard geometry:** the switch's 30-degree diverging leg plus the 8u yard minimum radius and the 2u straight between reverse curves give a siding about 3.4u from the main line, wider than the 1.6u minimum.
- **Speeds:** the main loop is 4.0 u/min, diverging legs 1.5 u/min, and the siding and spur 1.0 u/min (yard speed).
- **Tender load:** the tender carries cordwood, not coal, because engines start on wood (section 2).
- **Switch points:** the point rails do not animate yet. The target disc shows the setting.
- **Send to:** a moving train only takes a route in the direction it is already going; otherwise "Stop the train first." Routes are compared by estimated time (tender-first runs at 60%).
- **Changing direction:** Forward or Back the other way while moving sets mode `turn`: the train brakes to a stop, then runs the new way. A braking train (modes `stop`, `turn`) still looks ahead and stops 0.5u short of a switch set against it or a dead end.
- **Route locks:** freed on arrival, Stop or a new command. A switch under a train stays locked because it is occupied (`occupiedSwitches`), not by the route.
- **Saving:** IndexedDB (gzip) a couple of seconds after a world-changing action and every 10 game minutes; on page hide or close also an uncompressed quick save in localStorage (`railhead-quicksave`). On start the save with the higher tick wins. A damaged save is kept as `broken-<time>` (IndexedDB) or `railhead-broken-<time>` (localStorage) and the game starts fresh with a console warning.
- **Terrain (piece 3a):** per world (see "The real start"); the test yard 64 x 64 tiles of 2u (3.2u since D15), 2 x 2 chunks of 32 x 32 tiles, one shared vertex-colour material (up to 4 draw calls), plus a flat skirt beyond the map edge (its own mesh since M1 package 9, 1 more draw call). Hills come from seeded value noise (up to about 5.5u). The ground is held at height 0 within 7u of every track corner sample and over x -25..25, z -20..24, and fades to flat at the map edge. The heights are worked out again from the current track each time `buildTerrain` runs. `terrainHeight(x, z)` uses the same triangles as the mesh. The terrain receives shadows but does not cast them.
- **Day and night (piece 3a):** `daylightAt(time)` gives the light for a game time (no three.js); `applyDaylight` applies it. Colours and sun elevations follow design-doc 17. The intensities are tuned rather than copied from the doc (provisional, for the designer's review): noon stays at the approved sun 0.8 and sky 0.5, while dawn, dusk and night are lifted so the scene stays readable on a phone. Sunrise and sunset: spring and autumn 06:00 to 19:00, summer 05:00 to 21:00, winter 07:00 to 17:00. Because the game starts at 05:00, the first minutes are in dawn twilight. `GLOW_MAT` glows from just before sunset until just after sunrise.

## Manual switches (D20, builder SW)

No train ever throws a switch: the player does, at the stand (`useSwitch`, 0.5 game minutes, from either side). Code: "track graph" (`switchSpring`, `swName`, `swWant`, the comment above `trackIndex`), "game state" (`switchApproach`, `routeWrongAt`, `switchLockReason`), "routes" (`findRoute` needs carry `face` and `stopAt`; `routeNew`, `routeThrows`), "trains" (`trainTick`, `springPush`, `springTick`), "timetable" (`ttSwitchNeeds`, `ttSwitchPlan`, `ttRaPlan`, `swStation`).
- **Routes** (Send to and every timetable move, `ttGrant`) no longer set or lock switches. `tr.route.needs` = `[{ sw, state, face, stopAt }]` (stopAt: route distance to the switch's block: its node when facing, the far end of the leg when trailing). `trainTick` stops the train `CFG.STOP_GAP` short of the first one set the other way (`trackScan` already stopped a trailing move at a switch set against it, also for Forward and Back); it stands with `tr.swWait` = the switch (status "Waiting: the switch ahead is set against us", no number, as check-trains wants), event `trainSwitchWait`, alert `k: 'switch'` ("No. 1 is waiting at switch 2 (Willow Ford)") and one telegram. Thrown right, it goes on. Nothing is damaged: a trailing move never enters the switch.
- **Locks:** a switch under a train, or one a moving train would run over before it could stop (`switchApproach`: braking distance plus the stop gap, along the switches as set), cannot be thrown. A switch the train is stopping short of anyway can always be thrown right. `lockedBy` stays in the data, always null.
- **Send to** uses the switches as set: the `routeSet` event lists `throws` (`[{ sw, want }]`), the toast says which to set, and the train runs as far as it can and waits short of the first one. A route needing a switch another train stands on is refused as before.
- **Needs data for the work board:** `ttSwitchNeeds(S, day?)` (hooks: `__railhead.tt.ttSwitchNeeds`) -> `[{ svc, service, train, trainName, stop, move ('leg' | 'runaround'), station, stationName, sw, want ('normal' | 'reverse'), byTime (as S.time), by ('HH:MM'), spring, set, passed, done }]` in time order, for every timetabled service running that day. Routes are planned once per track and service from the stations' stopping tracks (`ttSwitchPlan`); byTime on a leg = departure + the leg's time in proportion to the distance to the switch; in a run-around the three moves at 1/4, 1/2, 3/4 of the dwell (estimates). `done` = passed, or set with no earlier move still wanting it the other way. A new timetabled day: 08:07 switch 1 reverse; 09:18 switch 2 normal (spring); 10:10 switch 3 reverse (spring); 10:30 switch 2 normal (spring); 12:34 switch 1 reverse; then the same for the afternoon (14:07, 15:18, 15:55, 16:07, 18:04).
- **Saving:** schema 16. 15 -> 16 frees every lock (`lockedBy` null, `route.locks` []), and in the real start makes switches 2 and 3 spring switches (levers N and R; a free one springs to its lever on the first tick). New fields: `W.spring`, `W.lever`, `tr.route.needs`, `tr.swWait` (only while waiting). An old route under way has no needs and runs on over the switches as they lie.
- **The M1 bot** (`switchTask`): throws the switch No. 1 waits at, or the earliest switch in `ttSwitchNeeds` not set for a move due within 3 hours, at the station it is at.
- **Check:** `tests/check-switches.js`.

### Provisional choices (switches, for the designer)
- **Willow Ford's run-around switches are spring switches** (it is unstaffed): switch 2 (west) lies for the main track, switch 3 (east) for the loop. Arrivals run to the platform, the engine runs out to the headshunt pushing 3 over (it springs back), back into the loop, out through 2 pushing it over, and onto its cars on the main. The player still uncouples the engine there, as before, and can throw either lever by hand (for a meet on the loop, for example). Without them the player would walk 64u between the two switches twice per run-around (about 25 to 30 game minutes each way).
- **A new game's platform switch (1) lies straight, for the main track (D22 (7), since 2026-11-04)**, so the player throws it to the platform track (reverse) before No. 1's first departure at 08:00 (needed by 08:07); every timetabled move goes through switch 1 reverse, so once thrown it stays right until the player sets it straight again (to the main track or the interchange). Set in `newState` (real start only), not in `buildStartWorld`/`startSwitchStates`, so saves keep their switches. (Until D22 it lay for the platform track and nothing needed a throw.) The interchange switch (0) lies for the main track.
- **The Overland needs no switch**: it comes in from the map's west edge on the interchange's own track and stops short of switch 0's connection, so nobody throws one for it today. **D22 (8) (designer): a switch in the Overland's way would be thrown by the player**, not by its crew (the D20 builder's provisional choice was its own crew); there is none in the layout now, so nothing is built for it. A later layout that puts one there must list it on the work board for the Overland's row and warn of it.
- A spring switch pushed over by a train counts as the train's wheels, not a throw; its lever never moves by itself.
- Send to goes as far as it can and the toast names the switches to set; the panel's status does not name switch numbers (the piece 1 review), but the alert, the telegram and the toast do (`switch N`, the id shown by Look).
